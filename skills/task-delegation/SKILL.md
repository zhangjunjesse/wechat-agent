# 任务委派细节手册（DESIGN-task-delegation.md / ADR-0024 / ADR-0025）

主对话把活派给后台子 agent，立刻回复用户、不阻塞；子任务完成后系统自动通知。
**判据（什么该派）不写在这里**：写在 ① `delegate_task` 的工具描述（每轮都在上下文，模型选工具时必然读到）
② 静态对话节奏规则第 4/5/6 条。理由见 ADR-0025——放在按需加载的文档里会系统性漏判。
本手册只解决「已经决定要派，接下来怎么做」。

## 1. goal 怎么写（决定成败）

子 agent **看不到你和用户的对话**，只看到 `goal` + `context`。写不清它就会猜。模板：

```
背景：<为什么做这件事，一两句>
目标：<要做出什么，可验证>
交付：<什么形式——文件（格式/命名）/ 一段总结 / 图片；发给谁>
成功标准：<怎样算做完>
边界：<不许做什么；信息不足时明确说缺什么，不要编>
```

`context` 只放**必需素材**：文档链接、用户偏好、上次相关结论——不要贴整段对话。

## 2. 派发与完成时怎么说

**派发后立刻回一句**（不要等、不要接着自己做）：

> ✅ 已派发任务 #3（导出《季度总结》为 PDF），完成后我把文件发你。

**不要说**：编造结果、"我看看哈"然后晾着用户、反复 `task_status` 轮询（完成会自动通知）。
**用户催问**（"在吗""好了吗"）→ `task_status`，如实答「还在处理中，已用 42 秒」，而不是"我马上就好"。

完成通知由系统发出（含任务 id 与结果摘要）。用户说「重试 #3」→ `retry_task`；
问「我派的任务怎么样了」→ `list_tasks`；问某个任务详情 → `task_status`。

## 3. 典型反例（每条都是真实踩过的）

| 反例 | 错在哪 | 正确做法 |
|---|---|---|
| 用户说"把这个飞书文档下载给我"，agent 直接调 `lark_export_doc` 等了 40 秒 | 用"我只调了一次工具"当判据。**单次调用也可能很慢**（异步导出 + 轮询） | 命中操作类型"导出/下载文件"就派发；由子任务去调那个慢工具 |
| 用户问"你能导出飞书文档吗？"结果真去派了任务 | 用户在问**能力**，不是在交代活 | 直接答能力，不要派 |
| 用户说"帮我改一下那个方案"，agent 猜着派了 | 需要澄清的活不能派（子 agent 无法追问用户） | 先问"改哪份、改成什么"，问清了再派 |
| 任务在几轮里长大（先要 PDF，再要 Word，再要 HTML），agent 每轮都自己做 | 没先 `list_tasks`，不知道已有进行中的同类任务，于是重复做 | 动手/派发前先 `list_tasks`，已有就报进度，别重复 |
| 派发后 agent 又自己动手做了一遍 | 派发等于移交，不做双份 | 只回一句"已派发"，去做别的事 |

## 4. 什么不必派（自己一句话答完）

能力询问、简单问答、单次查询、发一条消息；以及用户说「这个不用派，直接做」的类别。
敏感操作（删除、代发消息给别人、改线上数据）要逐步确认，不要交给后台。

## 5. 校准（用户反馈要记住）

用户说「这个不用派，直接做」或「这种以后都派出去」→ 记成用户偏好，后续同类任务按该偏好判断。
