# 任务板细节手册（DESIGN-agent-task-board.md / ADR-0025）

任务板是你自己的工作记忆：承诺（任务）落板，后台 drain 自动认领执行，完成后系统
自动通知用户。**判据（什么该落板）不写在这里**：写在 ① `task_create` 的工具描述
（每轮都在上下文，选工具时必然读到）② 静态节奏规则第 4/5/6 条。理由见 ADR-0025——
放在按需加载的文档里会系统性漏判。本手册只解决「已经决定落板，接下来怎么做」。

## 1. 任务怎么写（决定成败）

后台执行者**看不到你和用户的对话**，只看到 subject + description。写不清它就会猜。模板：

```
subject：<祈使句一句话，如"导出《季度总结》为 PDF 发给用户">
description：
  背景：<为什么做，一两句>
  目标：<要做出什么，可验证>
  交付：<什么形式——文件（格式/命名）/ 一段总结 / 图片；发给谁>
  成功标准：<怎样算做完>
  边界：<不许做什么；信息不足时明确说缺什么，不要编>
activeForm：<现在进行时，给用户看的，如"正在导出季度总结">
```

多件事各建一个任务；有先后就用 `blockedBy`（"先查资料再写文档" = 写文档 blockedBy 查资料）。

## 2. 建单与完成时怎么说

**建完立刻回一句人话**（不要等、不要接着自己做、不要展示板结构）：

> 记下了：先把资料查齐，然后给你出报告。做好我发你。

**不要说**：编造结果、"我看看哈"然后晾着用户、反复查询轮询（完成会自动通知）。
**用户催问**（"在吗""好了吗"）→ `task_get`/`task_output`，如实答「进行中，已 42 秒」，而不是"马上就好"。

用户说「重试任务 3」→ `task_update {status:"pending"}`；「不用做了」→ `task_update {status:"deleted"}`；
问「我那几件事怎么样了」→ `task_list` 后**人话转述**。

## 3. 完成纪律（违者是在向用户撒谎）

- 只有**完全做成**才 `task_update {status:"completed"}`——有报错没解决、交付物没产出、缺文件缺数据，都不许标；
- 被卡住 → 保持 in_progress，**新建一个任务写清卡点**（缺什么、等谁、下一步）；
- 改任务前先 `task_get` 读最新状态（板可能已被后台更新）；
- 自己当场做的（owner="me"）做完立刻标 completed，别让它挂在板上装作还在做。

## 4. 典型反例（每条都是真实踩过的）

| 反例 | 错在哪 | 正确做法 |
|---|---|---|
| 用户说"把这个飞书文档下载给我"，agent 直接调 `lark_export_doc` 等了 40 秒 | 用"我只调了一次工具"当判据。**单次调用也可能很慢** | 交付物类直接 task_create；由后台去调慢工具 |
| 用户问"你能导出飞书文档吗？"结果真建了任务 | 用户在问**能力**，不是在交代活 | 直接答能力，不建 |
| 用户说"帮我改一下那个方案"，agent 猜着建了 | 需要澄清的活不能落板（后台无法追问用户） | 先问"改哪份、改成什么"，问清了再建 |
| 同一件事几轮里反复建新任务 | 没先 `task_list` 查重 | 建前必查；已有就报进度 |
| 建完任务又自己动手做了一遍 | 落板等于移交，不做双份 | 只回一句确认，去做别的事 |
| 一件事拆成 5 个琐碎子任务铺满板 | 任务=有意义的交付单元，步骤活在执行里 | 一个交付物一个任务 |

## 5. 什么不必落板（自己一句话答完）

能力询问、简单问答、单次查询、发一条消息；以及用户说「这个不用记，直接做」的类别。
敏感操作（删除、代发消息给别人、改线上数据）要逐步确认，不要交给后台。

## 6. 校准（用户反馈要记住）

用户说「这个不用记，直接做」或「这种以后都记下来慢慢做」→ 记成用户偏好，后续同类按该偏好判断。
