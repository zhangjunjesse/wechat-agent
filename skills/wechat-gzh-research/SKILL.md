# 微信公众号内容调研 SOP

底层数据由 RedFoxHub（红狐数据）API 提供，通过本 agent 的两个工具访问：
- `gzh_search`：关键词 → 文章列表（标题/公众号/摘要/阅读/点赞/发布时间/workUuid，**不含正文**）
- `gzh_content`：workUuid → 单篇完整正文

工具不可用时（未配置 API Key 等），把工具返回的错误信息转述给用户，不要自己瞎猜。

## 执行流程（严格按顺序自己走完，不要每一步都停下来问用户）

### 1. 识别意图
把用户的自然语言请求拆解成：核心话题、用户真正想知道的角度（找热点讨论？找具体信息？看同行怎么写？）、隐含的范围限制（时间/账号类型/正反面观点）。

### 2. 生成关键词（多个，覆盖不同角度）
- API 硬限制：**关键词不超过 10 个字符**，超出会报错——长话题必须拆成短词，不能整句话丢进去。
- 一次话题至少准备 3～5 个候选关键词：核心词 + 同义/近义词 + 更具体的子话题词。例如话题"agent 安全"：`agent安全`、`AI安全`、`智能体安全`、`大模型安全`、`AI风险`。
- 不要一次只试一个关键词就下结论——公众号搜索对措辞很敏感。

### 3. 执行搜索
对每个候选关键词调用一次 `gzh_search`（count 默认 15 即可），收集结果。

### 4. 评估结果相关性
结合标题 + 摘要 + 公众号名判断是否真的相关，主动过滤培训班/引流广告类命中。给每条打相关性档位（高/中/低/不相关），参考阅读量（热度）和发布时间（时效）。

### 5. 判断是否需要调整关键词重试
- 高相关结果太少（少于 3～5 条能支撑一份调研）→ 换新角度关键词再搜一轮。
- 最多迭代 2～3 轮（累计关键词建议不超过 8 个），避免无限消耗 API 额度。迭代完还很少 → 如实告诉用户"这个话题在公众号腰部以上账号近 30 天的覆盖有限"，不要硬凑。

### 6. 去重、排序、精选
按标题/链接去重，高相关结果按热度+时效综合排序，选出值得深入看正文的候选（一般 3～8 篇）。**只对精选候选调用 `gzh_content`**——每抓一篇正文消耗一次额外额度，不要对所有结果都抓。

### 7. 抓取并核实正文
逐个调用 `gzh_content` 抓正文，检查正文是否真的在讨论用户关心的角度，还是标题党/摘要过度概括。丢掉的货不对板，必要时补抓候选。

### 8. 综合产出调研结论
最终只给用户一份组织好的结论，不要甩原始 JSON 或表格。建议结构：
- 一段总述：这个话题在公众号生态里目前的讨论热度/角度
- 分点列出关键发现（每点引用 1～2 篇文章的具体内容做支撑）
- 列出引用来源（标题 / 公众号 / 发布日期 / 链接），方便用户点开看原文
- 覆盖有限时明确说明限制，不要假装很全

### 9. 透明但不啰嗦地说明消耗
结尾带一句用了几次搜索、几次抓正文（例如"本次搜索尝试了 4 个关键词、精读了 5 篇正文"），让用户对额度消耗有感知。

## 常见问题

- **关键词超过 10 字符报错**：预期行为，直接换更短的关键词，不用向用户报错。
- **某关键词搜出 0 条**：正常现象，换关键词继续，不要就此终止。
- **用户给了具体关键词/公众号**：跳过第 1～2 步，直接按用户给的词搜；评估、精选、抓正文、成文仍要走完。
- **用户想追踪某个公众号的全部历史文章**：本技能不覆盖（这是关键词话题搜索），如实说明。
