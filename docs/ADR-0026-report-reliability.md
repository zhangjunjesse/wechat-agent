# ADR-0026: 日报可靠性修复——失败重试 + 补发不再靠模型现编

- 状态：Accepted
- 类型：Bug fix / Architecture（调度可靠性 + 工具分工）
- 日期：2026-09-16
- 关联：ADR-0017（日报管道）、ADR-0018（海报渲染）、ADR-0019（主题个性化）、
  ADR-0014（定时任务）、ADR-0025（委派判据——同一批事故里发现的姊妹问题）
- 触发：生产事故（真实会话，Z.俊 反馈"日报不对"）

## 问题（真实事故，双重故障）

2026-09-16 08:00:21（北京），`每日早报` 定时任务准时触发，但 LLM 调用报错
`402 Insufficient Balance`（账号余额耗尽——当天晚些时候切换到新的模型网关正是为了
解决这个问题）。用户收到一条兜底文字「生成失败，请稍后重试」，**当天再没有任何
早报**：模型切换后问题本已解决，但没有任何机制推动重新生成。

约一小时后用户说「日报补发一下」，agent 把它路由到 `get_daily_report`（一个为
"追问某条细节"设计、只返回纯文本的工具），模型据此**自己现编了一整段回复**：
9 月 15 日的旧内容、套了 `#`/`##`/`**粗体**`/`---`（微信不渲染 Markdown，用户看到
的是裸符号）、每条都带了原文裸链接。整个"海报图+短描述"的设计被完全绕开。

## 根因分析

| # | 根因 | 证据 |
|---|---|---|
| A | **调度器不区分"失败"与"成功"，两者都推进锚点** | `tasks.last_run_at` 无论成败都被写成"本次时间"，`nextRunAt(schedule, anchor)` 因此把下次触发算成"明天"——一次瞬时故障（限流/欠费/网络抖动）就让用户白等一整天，且没人会主动"稍后重试"。 |
| B | **"补发"没有专属能力，被路由到为别的场景设计的工具** | `get_daily_report` 的 description 明确写的是"追问某一条"，返回纯文本；它从未被设计成"把整份报告重新推一遍"，但模型在缺少更合适工具时把它当成了万能出口。 |
| C | **纯文本工具把决定权交给了模型的现场发挥** | 一旦工具只返回数据、不直接执行动作，模型就会自己组织表达——包括加 Markdown、摆裸链接，这些都是此前海报设计明确避免、但在这条旁路里complet复发的问题。 |

## 决策

### 1. 调度失败重试（根治 A）

`TaskScheduler` 的调度锚点语义收紧为**"最后一次结算时间"**（成功，或重试耗尽后
放弃）——不再是"最后一次尝试时间"：

- `TaskStore` 新增 `attempt_count`/`last_attempt_at` 列（迁移，默认 0，旧库自动补）；
  `markRun()` 语义收窄为"结算"（推进 `last_run_at`、`attempt_count` 归零），
  新增 `markAttemptFailed()`（只记尝试，不动 `last_run_at`，任务仍"到期"）。
- `#tick()`：到期任务若仍在重试中（`attemptCount>0`），按 `retryIntervalMs`
  （默认 20 分钟，env `TASK_RETRY_INTERVAL_MS`）节流；一天内最多重试 `retryMax`
  次（默认 3，env `TASK_RETRY_MAX`），即总共 `retryMax+1` 次尝试；仍失败才放弃
  并结算（等下一个自然周期，通常是明天）。
- **区分"生成失败"与"投递失败"**：只有生成本身（LLM/工具调用）失败才值得重试；
  投递失败（如 iLink 会话过期）重试生成解决不了问题，不占用重试预算，直接结算
  ——否则一个过期会话会白白多耗 2-3 次 LLM 调用。`#runForUser` 因此拆成两段
  try/catch，只有生成阶段异常才标 `retryable: true`。
- **失败话术如实反映状态**：还有重试机会 →「本次生成失败，系统会自动重试，
  无需操作」；重试耗尽 →「已重试 N 次仍失败，今天不再重试，明天按计划再试」——
  不再用含糊的"请稍后重试"（其实没有任何机制会真的重试，用户只能干等或来问）。

### 2. 补发走专属工具，不给模型现编的机会（根治 B/C）

新增 `resend_daily_report` 工具（`task-tools.mjs`）：直接调 `provider.sendImage` +
`provider.sendText` 重发**真实存过的海报文件 + 标准短描述**，工具执行本身就是
最终动作，模型只需一句话确认，不经手报告内容本身。

- 短描述复用 `daily-report.mjs` 新导出的纯函数 `renderPushText(report, { reportUrl,
  topics, resend })`——原始推送（`task-scheduler.mjs` 的 `#pushText`）与补发**共用
  同一份措辞逻辑**，两处不会再各写一套、行为跑偏。`resend=true` 时标注"🔁 …（补发）"
  避免用户把旧日期内容误当新推送。
- `get_daily_report` 收窄职责（改 description + 移除条目里的原文裸链接）：只做
  "追问某条细节"，并在描述里明确指向 `resend_daily_report`，防止再被当成万能出口。
- `findLatestReport()` 提取为共享查找逻辑，两个工具用同一份"该用户能看哪份报告"
  的判定，避免出现"改了一处、另一处没同步"的分裂。
- 门控与委派子 agent 一致：`resend_daily_report` 随 `reportStore` 一起注册，
  子 agent 的受限工具集（`taskStore:null/reportStore:null`）自动不含它。

## 备选（不选的理由）

- **只加宽 `get_daily_report` 的输出（让它也提示"有图"）**：治标不治本——只要
  最终发送这一步仍由模型的自然语言生成决定，就无法保证格式和是否真的带图，
  下次换一种问法（"再发一次""重推"）还会复发。
- **调度失败后立刻在同一 tick 里原地重试（无节流）**：一次真正的服务中断（如
  API 全面欠费到修复前）会让每 30 秒重试一次，白白刷调用量；节流+当日限次更稳妥。
- **所有失败都重试（不分生成/投递）**：过期会话这类"重试也没用"的失败会被
  无意义地重试 2-3 次，纯粹浪费 LLM 调用成本。

## 验收证据

- `node --test tests/*.test.mjs`：**336/336 全绿**（基线 330 + 新增 6：
  task-store 1——`markAttemptFailed`/`markRun` 的状态机语义；task-scheduler
  2——失败重试到放弃结算的完整生命周期、重试中途成功即结算；task-tools
  2——`resend_daily_report` 真发图+文、以及降级/拒绝分支；daily-report
  1——`renderPushText` 原始/补发两种变体）。
- 顺带修正：`send failures are aggregated into lastError` 测试补充断言
  `attemptCount === 0`，显式锁死"投递失败不占重试预算"这条区分。

## 遗留（诚实边界）

- **今天（9/16）的报告仍需人工补一次**：本 ADR 的重试机制只影响*以后*的失败——
  今天 8:00 那次失败已经把 `last_run_at` 结算在"今天"（旧代码行为，部署新代码前
  发生），不会被新逻辑自动追溯重跑。已通过手动触发一次生成来补齐（见部署记录），
  而不是留到明天才有早报。
- **多订阅者混合结果不重试**：报告类任务里"公共版失败、个性化版成功"（或反过来）
  这种混合结局按设计直接结算，不重试——避免给已经收到内容的用户重复推送；
  这意味着理论上存在"部分订阅者的那一份被漏发且不会自动补"的窄边界，目前
  接受（生产只有一个共享订阅者，未触及）。
- **没有失败告警面板**：重试与放弃目前只记录在 `tasks.last_error`，需要人工
  查库或等用户反馈才会发现；跨天持续失败没有主动告警机制。
