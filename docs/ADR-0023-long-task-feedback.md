# ADR-0023: 长任务进度反馈——延迟 ack + 心跳 + 失败必告知

- 状态：Accepted
- 类型：UX / Architecture
- 日期：2026-09-15
- 关联：ADR-0022（群命令入口）、ADR-0009（iLink 私聊推送）

## 问题

用户指派需要较长时间的任务（查群记录、读/导出文档、生成图片、调研）时，agent 要
**等任务全部完成**才响应，期间零反馈。用户不知道是在正常处理还是挂了，产生不安、
不可靠感甚至焦虑（用户原话："都不知道是不是异常，产生不安，不可靠，甚至焦虑感"）。

两个诱因叠加：① 多步工具任务本身要 1-3 分钟；② agent run 串行化（ADR 修复 400 时引入）
让并发消息排队，进一步拉长等待。

## 决策

### 1. 入口层统一进度反馈 `createProgressNotifier`（不依赖模型配合）

两个入口（私聊 `MessageRouter`、群命令 `GroupCommandWatcher`）共用同一组件：

- **延迟 ack**：任务 **8 秒**仍未完成 → 推「✅ 收到，正在处理，请稍候…」——短任务
  （问候、查时间）**不打扰**，长任务第一秒就有反馈；
- **心跳**：超过 40 秒后每 40 秒推一条进度（「⏳ 仍在处理中（已约 N 分钟）…」），
  **最多 5 条**（防刷屏）；任务结束（成功或失败）立即停止；
- **失败必告知**：agent 抛错时推「⚠️ 处理出错了：<原因>…可以再试一次」，**不再静默**
  （此前失败只写服务器日志，用户完全无感）；
- 无 contextToken / 非微信渠道 → 组件静默降级（网页渠道不适用）。

### 2. agent 侧主动汇报 `notify_user` 工具

多步任务中 agent 可**主动**推一条进度（"已查到 30 条记录，正在整理…"、"文档已导出，
正在发送…"），一次任务最多 2-3 次（工具描述约束，避免刷屏）。
配合静态层规则（`conversation-pace.mjs` 的 `PACE_RULES` 第 4 条）："预计需要较长的任务：
先说明再执行、分阶段汇报、最后给结果，不要长时间沉默后一次性倾倒结果"。

> 注（2026-09-16，ADR-0025）：`PACE_RULES` 第 4 条已改写为**任务委派默认动作**（操作类型清单），
> 本条"长任务先说明再执行 + 分阶段汇报"的语义由 `notify_user` 的工具描述 + 委派后的完成通知承接；
> 本 ADR 的 ack/心跳/失败必告知机制不变。

### 3. 分层职责

| 层 | 负责 | 为什么 |
|---|---|---|
| 入口层 notifier | 一定会有的"在干活"信号（ack + 心跳 + 失败告知） | 不依赖模型配合，可靠兜底 |
| agent `notify_user` | 有信息量的阶段汇报 | 依赖模型判断，锦上添花 |
| 静态规则 | 引导模型形成长任务习惯 | 行为方向，不写死话术 |

## 备选（不选的理由）

- **立即 ack（0 秒）**：短任务会多收一条噪音消息，打扰率 100%；8 秒延迟是最优折中。
- **只靠模型自己 ack**：首轮 LLM 响应本身就要几秒且不保证配合，可靠性不足。
- **无限心跳**：长任务会刷屏；上限 5 条 + 完成即停。

## 后果

- 长任务期间用户始终有反馈（ack → 心跳 → 结果/错误），焦虑感消除；
- 短任务体验不变（无额外消息）；
- 新增 1 个工具（`notify_user`）+ 1 个服务组件（`progress-notifier`），入口两处接入。

## 验收证据

- `npm test`：**308/308 全绿**（新增 7：progress-notifier 4——短任务无 ack / 长任务
  ack+心跳上限 / stop 静默 / 无 token 不发；message-router 3——失败必告知 / 慢任务
  ack+结果顺序 / 快任务无 ack；watcher 用例适配延迟 ack）。
- 生产部署并 healthz 200；`notify_user` 已注册进工具集。

## 遗留（诚实边界）

- 心跳文案固定，未按任务类型区分（如"正在查文档"/"正在生成图片"）——agent 的
  `notify_user` 可补充这类信息，但依赖模型主动调用。
- 未做"任务取消"（用户等不及想终止）；未做处理耗时的量化统计（可后续从埋点补）。
