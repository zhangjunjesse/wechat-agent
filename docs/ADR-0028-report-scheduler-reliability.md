# ADR-0028: 日报调度可靠性——重试按生成单元独立跟踪 + 调度器独享执行队列

- 状态：Accepted
- 类型：Bug fix / Architecture（调度可靠性 + 队列隔离）
- 日期：2026-09-16
- 关联：ADR-0026（失败重试机制——本记录把它的判定粒度收紧到单元级）、
  ADR-0027（按主题独立成篇——正是它让"一个任务多个生成单元"成为常态、
  暴露出本 bug）、ADR-0024（"独立实例 = 独立队列"隔离手法的先例）、
  ADR-0019（主题订阅）、ADR-0014（定时任务）
- 触发：用户提问「很多人都订阅、都在 8 点执行，会不会崩溃」——排查后确认
  不会因并发/内存崩溃（tick 串行循环、LLM 单实例串行队列、海报渲染一次性
  子进程，三处天然把并发钳死在 1），但顺藤摸出两个真问题。

## 问题

### 1. 重试判定粒度对不上（正确性 bug，与规模无关）

ADR-0027 之后，一个报告任务一轮 = 多个**独立**生成单元：无主题订阅者共享的
公共版 1 个 + 每个 (用户, 主题) 各 1 个。每个单元独立调 `#generateAndStore`、
独立成功/失败——但 ADR-0026 的重试决策仍是**任务级、全有全无**：
`retry = anyAttempted && !anySucceeded`，即"这一整轮一份都没成功"才重试。

只要任务下有 ≥2 个单元，"有的成有的败"几乎必然发生，此时：

- 任何一个单元成功 → `anySucceeded=true` → 整个任务被结算（`markRun`，
  锚点推到明天）——失败的单元**当天不会再被重试**；
- 更糟：失败单元的用户已经收到了 ADR-0026 的失败话术，若当时还不是最后一次
  尝试，文案是「系统会自动重试，无需操作」——**这个承诺不会兑现**，该用户
  今天就是没有重试、也不会再收到任何通知。

ADR-0026 的"遗留（诚实边界）"其实已经如实记下了这个窄边界（"混合结局按设计
直接结算……目前接受"），当时生产只有一个共享订阅者、未触及；ADR-0027 让
多单元成为常态后，订阅的人和主题越多，"部分失败 + 虚假承诺"发生的概率越高，
不能再接受。

### 2. 调度器和实时聊天抢同一条串行队列（潜在延迟风险）

`AgentsSdkAgent` 每个实例一条串行执行队列（`serial-queue.mjs`：防并发 run 互踩
DeepSeek thinking 缓存导致 400，历史事故见该文件注释）。`server.mjs` 的主
`agent` 实例被三处共用：`MessageRouter`（私聊）、`GroupCommandWatcher`（群
@ 命令）、`TaskScheduler`（个人定时任务 + 日报生成）——8 点这一批日报生成会
跟"这一刻正在聊天的任何用户"抢同一条队列。当前规模（1 订阅者 2 主题）没事；
订阅规模上去后（`MAX_REPORT_TOPICS=5`，总生成次数 = Σ 每人主题数），忙碌窗口
会拉长到分钟级，期间任何人的私聊、群命令、其他人的个人定时任务都可能被拖慢
（`#tick()` 不可重入，同一 tick 里排后面的任务乃至下一次 tick 都会被耽搁）。

## 决策

### 1. 重试判定单元从"整个任务"下沉到"每个生成单元"

- `TaskStore` 新增 `retry_units` 列（迁移风格同 ADR-0026 的 `attempt_count`：
  `PRAGMA table_info` 探测 + `ALTER TABLE` 补列，默认 `'[]'`，旧库自动补）：
  JSON 数组，记录本结算周期内**还在等重试**的单元及各自尝试次数，如
  `[{"userId":"u1","topic":"AI","attempts":1}]`；公共版单元用
  `userId=''、topic=''` 表示。新增 `setReportRetryUnits(id, units)` 覆写；
  `markRun`（整体结算）一并清空该列——昨天的失败单元不泄漏进明天的新周期。
- `#runReportTask` 改为按单元执行：首轮（`retry_units` 为空）跑全部单元；
  失败单元（含 `report_unparsable` 降级）连同尝试次数写入 `retry_units`；
  **重试轮只重跑还挂着的单元**——已成功的用户绝不被重复生成/重复推送
  （对应非 report 路径早已有的 `results.every((r) => r?.retryable)` 约束，
  report 路径至此有了对应的按单元版本）。期间退订/删主题导致单元消失的，
  直接出局不再跟踪。
- 结算条件收紧为：**所有最初尝试过的单元都成功或耗尽重试次数**，任务才整体
  `markRun`（锚点推到下一周期）；只要还有单元挂着就返回 `retry=true`，走
  ADR-0026 原有的 `markAttemptFailed` + `retryIntervalMs` 节流路径。两级计数
  天然同步：首轮跑全部单元、重试轮只跑挂着的单元，因此单元的 `attempts`
  恒等于任务级 `attempt_count`，`#tick()` 的节流与放弃门控原样复用，零改动。
- 失败话术按**该单元自己**的重试余量措辞：说「系统会自动重试」当且仅当这个
  单元真的还会被重试；说「今天不再重试，明天按计划再试」当且仅当这个单元
  自己耗尽——不拿别的单元的命运替它承诺。

### 2. 调度器独享一个 `AgentsSdkAgent` 实例

`server.mjs` 给 `TaskScheduler` 单独 `new AgentsSdkAgent(...)`（`schedulerAgent`），
与 `MessageRouter`/`GroupCommandWatcher` 共用的主 `agent` 分开——实时聊天和
定时任务/日报生成走两条互不干扰的串行队列。隔离手法是 ADR-0024 委派子 agent
的先例（独立实例 = 独立 thinking 缓存 + 独立队列），但语义有意不同：

- **全量工具集**（与主 `agent` 同一个 `tools` 数组引用，含 delegate 工具），
  不是 `makeSubagent` 的受限版——这里隔离的是队列，不是权限；
- **同一份数据源**：`...sessionOpts` 展开的是同一个 `sessionStore`/`memoryStore`
  对象引用（同一个 `data/sessions.db`/`data/memories.db`）——`#runForUser`
  （个人定时任务）传真实 `userId`/`profile` 写用户真实会话历史，数据源若分叉，
  定时任务的对话就会跟用户的真实聊天记录分家。日报生成本来就是
  `ephemeral: true` 的合成 userId，不碰真实会话，两边都安全。

## 备选（不选的理由）

- **保持任务级判定、失败话术改口不承诺重试**：只修话术不修行为，用户该没
  收到的那份还是没有——ADR-0026 的初衷（"不能让用户干等一个不存在的重试"）
  等于白做。
- **部分失败时整任务重跑（全单元重试）**：已成功的用户会被重复推送同一份
  海报——ADR-0026 明确不接受（"避免给已经收到的人重复推送"），这也是当时
  选择"混合结局直接结算"的原因；正确解是按单元跟踪，不是在"全重跑"和
  "全放弃"里二选一。
- **待重试单元放内存（调度器实例字段）**：`#tick()` 之间进程可能重启（部署、
  崩溃），内存状态一丢就退化回任务级行为，且与 ADR-0026"重试状态必须落库"
  （`attempt_count` 进 SQLite）的既有决策不一致。
- **新建一张 retry 明细表**：一个任务同一时刻只有一份待重试集合，生命周期与
  结算周期严格绑定（结算即清空），单列 JSON 足够；独立表要多一套增删改查和
  联表清理，复杂度不换任何能力。
- **问题 2 用"错峰"（把日报挪到低峰时段）替代队列隔离**：治标——个人定时
  任务是用户自定的任意时刻，错不开；且聊天没有"低峰保证"。
- **问题 2 复用 `makeSubagent`**：它配的是受限工具集（防递归委派），调度器
  的 agent 需要全量工具（定时任务指令可自由使用工具/技能），语义不对。

## 验收证据

- `node --test tests/*.test.mjs`：**345/345 全绿**（改动前基线 342，净增 3：
  task-scheduler 2——部分失败只重试失败单元、已送达用户不被重复推送、失败
  单元后来成功才整体结算；单元连续失败到耗尽收到"今天不再重试"话术、任务
  结算锚点推到明天、同伴单元全程只推送一次；task-store 1——`retry_units`
  迁移默认值/覆写/`markRun` 清空的状态机语义）。
- 既有测试`one topic failing does not block another topic for the same user
  (ADR-0027)` 的结算断言随语义修正（原断言 `lastRunAt > 0` 锁的正是本次要修
  的"部分失败即结算"行为）：改为断言任务**不**结算、失败单元进 `retry_units`；
  该测试的本意（一个主题失败不拦住另一个主题当轮送达）原样保留。
- ADR-0026 的全部重试测试（全失败→节流→耗尽→结算、中途成功即结算、
  unparsable 降级、投递失败不占重试预算）不改一字全绿——单一单元场景下
  新旧判定等价。
- 队列隔离：仓库无 server.mjs 接线的直接单测先例（一贯做法是组件级测试 +
  代码核实，如 `delegate-tools.test.mjs` 只复刻 `buildTools` 的构造参数），
  按同一惯例以代码核实：`src/server.mjs` 现有两处独立的 `new AgentsSdkAgent`
  （主 `agent` 与 `schedulerAgent`），`AgentsSdkAgent` 的
  `#runQueue = createSerialQueue()` 是实例字段初始化器——每个实例必然各持
  一条队列；两处构造展开同一个 `sessionOpts` 对象（同 `sessionStore`/
  `memoryStore` 引用）、同一个 `tools` 数组引用。

## 遗留（诚实边界）

- **忙碌窗口只是被隔离，没有被缩短**：日报生成总量随订阅规模线性增长的问题
  仍在（ADR-0027 遗留里的"按主题分组缓存"仍未做）——本记录只保证它不再
  拖累实时聊天；调度器自己这条队列里，晚触发的个人定时任务仍会排在日报批次
  后面。
- **投递失败仍不重试**：生成成功但推送失败（如 iLink 会话过期）的单元按
  ADR-0026 的既有区分直接算作已处理，不进 `retry_units`——重试生成解决不了
  投递问题，该边界维持原状。
- **跨周期未结算的极端场景**：若进程恰在重试周期中间停机到第二天，重启后
  `retry_units`/`attempt_count` 延续上个未结算周期继续跑（与 ADR-0026 的
  `attempt_count` 行为一致），当天的新一轮要等上个周期结算后才开始——
  维持既有语义，未特殊处理。
- **队列隔离未经生产压测**：两实例分队列的效果（8 点批量生成期间聊天不被
  拖慢）逻辑上成立、代码已核实，但真实高峰表现需生产观察；目前订阅规模
  （1 订阅者 2 主题）触不到这个窗口。
