# ADR-0038: 固定反馈管道——分诊先行，反馈点由代码写死

- 状态：Accepted（已实现并通过全量测试；生产部署与真实分诊验证随本记录执行）
- 类型：Architecture / Product（对话主链路重构）
- 日期：2026-09-18
- 关联：ADR-0036（任务板——本管道的执行底座，plan 落板即板任务）、
  **ADR-0037（部分修正：其"1:1 慢轮次零反馈"的代价条款被 task 路的受理回执
  收窄——chat 路"无 ack、一条直答"的结论原样保留）**、
  ADR-0035（失败分类/静默/话术，批次通知沿用）、ADR-0025（判据文本复用进
  分诊 prompt；主 agent 的 task_* 工具保留为分诊漏判的第二道网）、
  ADR-0015（时间间隔感知——后台通知会刷新 updated_at，通知也算助手说话，接受）
- 需求授权：产品负责人 2026-09-18 原话「我想要的效果类似 coding agent……
  理解任务后立马给一个回馈，然后安排子任务；子任务完成之后主动告诉我；
  我要固定的 LLM 之外的规则」+「我不看了，你全部搞定」（全权委托）。

## 问题

`agent.respond()` 是黑盒：整个 loop（理解→工具→再想→答）跑完才吐一条 text，
架构上没有任何缝隙可以插反馈。用户交代一个任务，微信里"全部做完之后统一答复"
——过程零可见。此前两轮尝试（ack 阈值调整、工具描述纪律）都在调"模型自觉"，
方向性错误：**反馈必须是管道的固定产物，LLM 只能填内容，不能决定发不发**。

## 决策

一条用户消息的处理切成代码固定的两条路（`turn-pipeline.mjs` + `triage.mjs`）：

```
消息 → 分诊（轻量 LLM：无工具/关思考/temp 0，输出 {kind, ack, plan}）
  ├ chat → 主 agent respond 原路径（一条直答，管道零介入）
  └ task → ① 受理回执（~3s，代码发；文案来自分诊，缺失用兜底模板）
           ② 回执 sendText 成功后才 commit：plan 机械落板（两趟：先建全部
              任务再补依赖边——plan 允许前向引用）+ 共享 metadata.batchId
              + poke drain
           ③ 每个子任务结算 → 通知带 (n/N) 进度（runner 代码发）
           ④ 批内全部尘埃落定 → 收尾说明**合并进最后一条**通知（不另发）
```

**固定规则（全部有测试钉死）**：

| # | 规则 | 落点 |
|---|---|---|
| R1 | 分诊失败/超时(8s)/JSON 修不好/plan 校验不过 → 一律降级 chat；`route()` 永不 throw。**分诊器彻底坏掉 = 系统退化成管道上线前，不会更糟** | triage.mjs / turn-pipeline.mjs |
| R2 | plan 代码校验：1-5 个、subject 非空、dependsOn 下标合法、DFS 防环 | triage.mjs |
| R3 | task 路回执**必发**：ack 缺失用兜底模板"收到，我来办：…"，超 80 字截断 | triage.mjs |
| R4 | 保守偏置：不确定/信息不完整/对已有任务的追问操作 → chat（误判不对称：闲聊被建任务比任务被慢答更伤）；分诊输入含活跃任务清单与附件路径 | prompt + turn-pipeline |
| R5 | 时序：回执发送成功之后才落板（防子任务极快时完成通知先于回执） | message-router / app.mjs 调用顺序 + commit 契约 |
| S1/S5 | commit 里 `append(用户消息, 回执)` 进 session + `memory.absorb` 同对 | turn-pipeline |
| S2 | 后台推送的每条通知 `appendAssistant` 进 transcript（无推送通道也记——板上有结果，下轮对话要能指代） | subagent-runner |
| — | `TURN_PIPELINE=0` 保险丝：整体关闭，所有消息走原路径 | server.mjs |

**批次语义**：同一次分诊落板的 plan 共享 `metadata.batchId/batchSize`；
"尘埃落定" = completed/deleted 或 pending 且退避顶满。单任务批次 = 普通通知
（无进度标记）；多任务批次每条带 (n/N)，最后一条并入收尾统计（含失败：
"1 件完成，1 件没做成"）。deleted 收尾不发消息（用户主动取消，他知道）。

**并发写澄清（更正一处早期审计结论）**：`SessionStore.append/appendAssistant`
为纯同步（node:sqlite 同步 API、全程无 await）——JS 单线程下两个同步块不可能
交错，跨实例并发写 session 的"读-改-写竞态"**不存在**。后台 runner 写 session
无需加锁。

## 备选（不选的理由）

- **继续调模型自觉**（prompt/工具描述让它先回一句）：两轮实证失败——模型在
  一个黑盒 run 里根本没有"先发一条"的通道，且是否照做是概率性的。
- **恢复 ADR-0023 式通用 ack**：8s 基线压阈值、"收到正在处理"无信息量，
  用户明确否掉；受理回执与它的本质区别是**有内容**（复述理解+计划）且仅 task 路。
- **消息流式输出**：iLink 无流式语义。
- **分诊与主 agent 并行起跑**（省 chat 路 +3s）：task 判定时要丢弃已启动的主
  run，且与串行队列互堵，复杂度不成比例。落选，+3s 作为已接受代价（下条）。

## 后果

- task 路：~3s 受理回执 → 过程通知 → 收尾，coding-agent 式可见性，全部代码保证；
- 受理回执同时是**用户否决窗口**（plan 自动执行、无人工确认环节，3s 内看到
  "我要做 X 和 Y"说一句"别做"即可取消）——这是明确职责，不是副产品；
- **代价：chat 路每条消息 +~3s**（分诊串行在前，简单问题 8s→11s）——用 3 秒
  买 task 路 3 秒首反馈；短路优化（≤4 字问候直判）留待观察后再议；
- 每条消息 +1 次轻量 LLM 调用（≤600 token 输出，成本可忽略）；
- 分诊误判把任务判成 chat → 退化为一条慢答复（主 agent 的 task_* 工具是第二道
  网）；判成 task → 多一条回执 + 后台跑一趟，回执可见让用户能当场纠正。

## 遗留（诚实边界）

- **分诊准确率未知**——prompt 判据只能上线观察；`[triage]` 决策日志逐条留痕，
  失误可回答"为什么这条被当成了闲聊"。
- task 路不触发会话折叠（fold 连着 compactor 的 LLM 调用，活在主 agent
  respond 里）；用户任意一次 chat 轮次会把折叠追上。
- 网页端发起的任务，后续通知只到微信（网页无推送通道）；网页任务状态 UI 留待。
- 群命令入口未接管道（有自己的 ack，行为不一致，待统一）。
- 执行中的修订 = 主 agent 取消重建（粗糙但语义正确）；子任务粒度失控靠
  prompt 软约束 + 超时率观察。

## 追加（2026-09-19）：结算通知文案面向用户化

用户反馈"任务 #N 完成：…"像机器日志。四条约定的补充：

1. **成功通知不暴露内部任务编号**，用意图（subject）当标题、正文只放结果；失败通知**保留编号**，因为"重试任务 N"要用户可复制。
2. **子 agent 只写面向用户的答复**（prompt 第 4 条）：不写过程叙述、不写"任务完成/结果说明"这类标题、不提内部编号。内容仍由 LLM 生产，格式化仍由代码固定——不改 ADR-0038 的"固定规则"原则，也不为此新增 LLM 调用。
3. **截断落在句末**：正文最多 2 段、约 180 字，超出时回退到最近的句号/换行收尾，不再硬切在句子中间（此前 200 字硬切会切出"…让我先尝试搜"这类残句）。
4. 批次进度 `(n/N)` 与收尾合并规则不变。

验证：`tests/subagent-runner.test.mjs` 13/13（含"成功通知不含 任务 #N"与"长结果在句号处收尾"两条新断言）；全量 531/531。
