# ADR-0008: 沙箱代码执行工具 + 文件下载链接

- 状态：Accepted
- 类型：Architecture / Feature
- 日期：2026-08-26

## 问题

真实使用中暴露了两个具体失败（不是假设的）：

1. 用户贴了约 80 条联系人记录，要求按性别+签名筛选、去重。模型在回复里**手动逐条核对**，
   中途重新数了一遍还是有出入——LLM 不擅长精确的批量数据核对，靠"在自然语言里数数"
   本质上不可靠。
2. 模型说"我把文件写好给你"，但 `write_file` 只能写到服务器沙箱目录：iLink（微信）
   通道只有 `sendText`，没有发文件/图片的能力（协议本身没有实现过，也没有验证过存不
   存在）；网页也没有任何文件浏览/下载路由。用户在任何一条通道都拿不到这个文件——这是
   一个兑现不了的承诺。

用户明确要求"先在现有 OpenAI Agents SDK 底座上补这两个能力，不整体换底座"（对照过
换成 Claude Agent SDK 的方案：它自带 Bash/代码执行，但把 Bash 暴露给多租户陌生用户
是我们从一开始就排除的 C 类能力；且换底座不会自动带来文件投递能力，也需要重新搭建
已经跑通的多租户会话/记忆/技能隔离）。

## 决策

### 1. `run_code` 工具：worker_thread 隔离 + 空对象注入的 vm 沙箱

新增 `src/tools/code-tools.mjs` + `src/tools/code-worker.mjs`。模型可以写一段同步
JavaScript，对 `input`（字符串）做过滤/去重/排序/统计/拼接，最后一行的表达式值就是
返回结果（REPL/eval 语义，没有 `console.log`、没有 `return`）。

**安全模型（诚实说明边界，不夸大）：**

- **每次调用起一个独立 `worker_thread`**，不在主进程里跑：脚本卡死、内存暴涨，最坏
  情况只会让这一个 worker 被杀掉（`resourceLimits` 限制堆大小），不会拖垮承载其他
  用户对话的共享服务进程。这是这次设计里最重要的一层防护，实测过：一个不断分配内存
  的死循环脚本在 ~60ms 内就被限制终止，没有影响后续调用。
- **vm 上下文只注入一个纯字符串 `input`，不注入任何函数/对象**。这是刻意的选择：
  vm 沙箱最经典的逃逸手法是"拿到一个宿主注入的回调函数，顺着它的
  `.constructor.constructor` 摸到外层的 `Function` 构造器，从而在外层作用域执行
  代码"——这个手法的前提是沙箱里存在至少一个宿主对象。只传字符串（原语类型没有这条
  逃逸路径）就从设计上避免了整类问题，代价是沙箱里没有 `readFile`/`writeFile`/
  `console.log` 这些便利函数（模型要落盘就必须另外调 `write_file`，是两次工具调用
  而不是一次，但换来攻击面显著变小）。
- **实测验证，不是纸上假设**：Node 的 `vm` 模块会自动往每个上下文注入一个
  `console`（不是我们加的，删不掉）。专门写了一个回归测试
  （`tests/code-tools.test.mjs`）用"跨 realm 标记"验证：`console.log.constructor
  .constructor` 这条经典逃逸路径在当前 Node 版本（22.23.x）上**被挡住了**，摸不到
  真实的外层作用域。测试锁定了这个结论——如果未来 Node 版本改变这个行为，测试会
  立刻失败，而不是等到生产上出问题才发现。
- **超时**：用 `vm.runInContext` 自带的 `timeout` 选项（V8 中断机制，真能打断
  `while(true){}` 这种同步死循环，不是普通 JS 定时器那种"打断不了同步代码"的假
  超时），加上 worker 一层强制 `terminate()` 兜底。
- **诚实的局限**：Node 官方文档原话是"vm 模块不是一种安全机制"。这里做的是"验证
  过经典逃逸手法被挡住 + 只传原语值 + worker 线程隔离资源耗尽"，是一套**尽力而为**
  的沙箱，适合"已核验身份的微信用户 + LLM 生成的数据处理脚本"这个场景，**不是**
  对抗蓄意攻击的硬边界。如果未来场景变成接收匿名/不可信输入，需要升级到进程级/
  操作系统级隔离（比如给每次执行单独开一个受限容器），而不是继续信任内置 `vm`。
  另外 worker 线程本身仍有完整 Node 能力（文件系统、网络）——worker 隔离防的是
  "崩溃/资源耗尽波及主进程"，如果未来真的出现新的 vm 逃逸手法，worker 隔离本身
  **不能**阻止逃逸后的代码访问网络或本机文件系统，这是残留风险，当前用"已核验用户 +
  已验证过经典逃逸手法被挡"来控制，不是"零风险"。

### 2. 下载链接：不可猜测的 token，而不是登录态

新增 `src/services/download-tokens.mjs`（`DownloadTokenStore`）+ `app.mjs` 的
`GET /files/:token`（同时挂在 `/wechat-agent/files/:token`，跟 assistant-qr.jpg
的双路径模式一致）。

- **为什么不用现有的 `x-user-id` 头**（`/api/*` 那套鉴权）：用户在微信里点的链接，
  是手机自带浏览器发起的普通 GET 请求，没有办法带自定义请求头；为了下载一个文件
  让用户先登录网页，对聊天机器人这个场景是不可接受的体验成本。
- **方案**：`write_file` 成功后签发一个随机 token（`crypto.randomBytes(24)`），
  映射到 `{userId, relPath}`，存内存（不持久化——token 只是为了"生成后不久就点开"
  这个短时窗口，容器重启丢失可以接受，模型可以重新生成文件和新链接）。默认有效期
  24 小时（`DOWNLOAD_TOKEN_TTL_MS`）。
- **token 本身就是权限凭证**（跟任何"分享链接"同一套信任模型）：知道 token 才能
  下载，且一个 token **只能**读到它签发时绑定的那一个文件，不能浏览目录、不能换
  别的路径——即使 token 泄露，最坏情况也只是那一个文件被看到。
- 下载路由收到 token 后，仍然用共享的 `resolveUserPath`（跟 `file-tools`/
  `run_code` 同一个沙箱边界函数）重新校验一次路径，双重保险。

### 3. 系统提示词新增"工具使用规则"

`buildBaseInstructions` 里安全规则之后新增一段，直接对应上面两个真实失败：

1. 批量数据的筛选/去重/计数/排序必须用 `run_code`，不许手动数。
2. 有下载链接才能说"给你文件"，没有链接不许说这类无法兑现的话。

## 备选方案（不选的理由）

- **整体换 Claude Agent SDK**：它自带 Bash/代码执行，但这次问题的一部分（文件投递）
  跟 SDK 无关，换了也不解决；另一部分（Bash 权限）恰恰是我们从项目一开始就明确排除
  给多租户陌生用户的能力（C 类）。真要用，还是得先把 Bash 收窄到跟现在同等窄的白
  名单，等于在更重的底座上重新做一遍现在已经做好的沙箱，还要重新搭一遍已经跑通、
  测试覆盖、生产验证过的多租户会话/记忆/技能隔离。不选。
- **`node:vm` 直接在主线程跑，不开 worker**：省掉 worker 启动开销和消息传递复杂度，
  但一个内存炸弹脚本能直接拖垮承载所有用户对话的主进程——对一个多租户服务来说这个
  风险不能接受。不选。
- **调研/实现真正的 iLink 文件发送**：iLink 协议目前只验证过 `sendmessage` 的
  文本类型（`item_list[].type===1`），其它 message_type 未经文档确认、未经测试，
  贸然拼接未验证的字段有把生产收发消息搞坏的风险。改用现有已经在跑的 web 层加一个
  下载路由，风险低得多、且立刻可用。不选（不代表以后不做，只是这轮不做未经验证的
  协议猜测）。

## 验收证据

- `tests/code-tools.test.mjs`：精确过滤去重（对应真实失败场景）、沙箱内无
  `process`/`require`/`fetch`/`Buffer`/`global`、**经典 vm 逃逸手法的回归测试**
  （跨 realm 标记验证逃逸失败）、超时终止死循环、内存炸弹被 worker 资源限制终止、
  无返回值/抛错的友好提示、输出截断。
- `tests/download-tokens.test.mjs`：签发/解析、单文件作用域隔离、TTL 过期、
  单次签发可覆盖默认 TTL。
- `tests/file-tools.test.mjs`：`write_file` 在有/无 `issueDownloadLink` 时的
  行为分别验证。
- `tests/app.test.mjs`：`GET /files/:token` 真实 HTTP 请求验证——正常下载、
  双路径（含 `/wechat-agent/` 前缀）、未知 token 404、伪造路径不能越权读到别的
  用户文件。
- `tests/system-prompt.test.mjs`：工具使用规则文案存在性。

## 遗留

- iLink 是否支持发文件/图片：未调研、未验证，仍是"不知道"，不是"确认不支持"。
- worker 逃逸后仍具备该 worker 自身的文件系统/网络能力，这是尽力而为沙箱的诚实
  残留风险，见上文"诚实的局限"。
