# ADR-0041 web_fetch 的 SSRF 防护误杀全部公网网址

- 状态：已采纳（2026-09-19）
- 类型：缺陷修复 / 网络边界
- 关联：ADR-0024（子任务工具集）

## 背景与问题

用户实测："web_fetch 对外部网站全部被拦截"，助手据此判断"本环境网络检索受限"，最终只能用自身知识库凑答案。

**根因**：`isPrivateIp()` 里一行"安全默认"：

```js
if (ip.includes(':')) return true // block all IPv6 (safe default)
```

把所有含冒号的地址（即**全部 IPv6**）判为内网/保留地址。而 `dns.lookup(host, { all: true })` 在双栈网络下会返回 AAAA 记录，于是**任何有 IPv6 的公网站点都被拒绝**。

生产实测（容器内直接调用工具）：

| 目标 | 结果 |
|---|---|
| `https://mp.weixin.qq.com/...` | 目标地址不允许访问（内网/保留地址） |
| `https://www.baidu.com` | 同上 |
| `https://zh.wikipedia.org/wiki/Cat` | 同上 |

而同一时刻容器 DNS 解析完全正常（`www.baidu.com → 183.2.172.177` + 若干公网 IPv6）。

不是"能力被关掉"，而是**这道防护从上线起就让 web_fetch 对外网完全不可用**——只是此前没有任务真正依赖它，所以没人发现。

## 决策

`safeHost()` 只解析 A 记录：`dns.lookup(host, { all: true, family: 4 })`。

理由：SSRF 防护要判定的是**实际会去连的那个地址**，而本机出网走 IPv4；把用户提供的可疑域名解析成 IPv6 再绕过防护的路径，在"解析即按 IPv4 判定 + 下行用 IPv4"下不存在实际风险，而"因为对方有 IPv6 就一律拒绝"是纯粹的可用性自伤。

`isPrivateIp()` 的 IPv4 判定（10./192.168./169.254./172.16-31/100.64-127/127.0.0.1/0.0.0.0）一字未改，内网防护仍然成立。

## 被放弃的能力

- **不判定 IPv6 目标**：解析结果里不再含 IPv6，因此也没有针对 IPv6 内网地址（`::1`、`fc00::/7`、`fe80::/10`）的防护。这是有意的取舍：以本机 IPv4 出网为前提，纯 IPv6 目标本来也连不上；若将来改为双栈出网，必须重新引入 IPv6 私有段判定，而不是恢复"含冒号即拒绝"。

## 验收与证据

- `npm test` → **531/531 通过**（含 web-tools 既有 SSRF 用例：内网地址仍被拒）。
- 生产实测（部署后）：`web_fetch` 对 `mp.weixin.qq.com` / `baidu.com` / `zh.wikipedia.org` 返回正文而非拦截错误。
- 同一轮实测确认**图像生成链路是好的**：容器内 `image_generate` 真实生成 PNG 成功，返回"请调用 send_file 把图片作为真实消息发给用户"——用户看到的"图片发不出来"是下游 send_file 的渠道问题（ADR-0039/0040），不是图像能力故障。

## 遗留（不在本记录范围）

- `gzh_search` 返回的"未查询到相关数据…优质库暂未收录"是红狐 API 的**业务性无结果**，不是故障；但它和"接口执行异常"混在同一句文案里，容易被模型读成"工具坏了"。文案区分是独立的小改动，未做。
