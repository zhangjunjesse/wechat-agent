# ADR-0006: 技能强制调用 + 同轮去重

- 状态：Accepted
- 类型：Feature
- 日期：2026-08-25
- 相关：ADR-0005（按用户隔离的技能机制）——本记录只改"怎么触发/加载一次"，不改隔离边界

## 问题

`use_skill` 上线后（ADR-0005）是一个"软"机制：模型看到系统提示词里的技能目录（名字+一句话描述）后，**可以不调用就凭猜测执行**，也可能"提到某技能存在"却不实际调用它去取完整指令。这样技能正文里的步骤/约束就形同虚设。

参考 WorkBuddy 的 Skill 工具设计：它在工具描述里写了 `BLOCKING REQUIREMENT`（技能匹配时必须先调用，不得跳过）+ `NEVER mention a skill without actually calling this tool`，并用 `<command-name>` 标签防止同一技能在同一轮里被重复加载全文。这是我们之前判断"现在值得学"的两条（其余如 `args`/命名空间/`ToolSearch+DeferExecuteTool` 判定后置）。

## 决策

1. **强制调用语义**：`use_skill` 工具描述 + 系统提示词技能目录的表头文案，都加入"匹配技能后必须先调用本工具，不得凭猜测直接执行，也不得只提及技能名却不调用"的约束。这是**提示词层面的引导**，不是代码强制（模型仍可能不遵守），但把约束写清楚是必要前提。

2. **同轮去重（`<command-name>` 的等价物）**：我们没有 WorkBuddy 那种客户端"已加载标签"注入机制，改用运行时状态实现等价效果——`AgentsSdkAgent.respond()` 每次对话给 `run()` 的 `context` 挂一个新建的 `loadedSkills: Set()`；`use_skill` 执行时：
   - 首次加载某技能：返回完整指令，并把技能名记入 `loadedSkills`；
   - 同一轮（同一次 `respond()` 调用期间，模型可能多次调用工具）再次请求同一技能：不重复返回全文，只提示"本轮已加载过，按之前指令执行即可"——防止同一段长指令反复占用上下文。
   - **作用域是"一轮对话"，不是"会话"**：`loadedSkills` 随 `respond()` 调用新建，下一轮用户消息会重新允许加载（因为 transcript 里可能已经把上一轮技能指令折叠掉，模型需要能重新取）。

## 备选方案

1. **不做去重，每次都重新返回全文**：简单，但技能正文长的话会重复消耗 token；不选。
2. **按会话（session）级去重，而非按轮（turn）级**：更省 token，但技能指令一旦被会话摘要折叠掉，模型后续拿不到就没法再次加载——不选，去重范围必须小于等于"指令还在活跃上下文里"的范围，轮级最安全。
3. **完全照抄 `<command-name>` 标签机制**：那是 WorkBuddy 客户端在渲染层插入的标记，我们的 harness（OpenAI Agents SDK）没有等价接口；用 `run context` 里的 `Set` 做等价的运行时状态，效果一致、实现更简单。

## 后果

- `use_skill` 描述与技能目录表头都变长了（多了强制调用的说明文字），会消耗更多静态 instructions token；技能数量增多后如果这段文案显得冗余，可以再精简。
- 去重是"尽力而为"的软约束，不能阻止模型完全无视工具直接编造执行结果；根本约束仍在技能正文本身写清楚"必须先做什么"。
- `ctx.context.loadedSkills` 是新增的 run-context 字段，工具需要做防御性判空（`loaded?.has/add`）以兼容没有传入该字段的调用方（如现有测试直接构造 `ctx`）。

## 验收证据

- `tests/misc-tools.test.mjs`：
  - `use_skill.description` 含"必须先调用"、"不得凭猜测/不要凭猜测"关键词；
  - 首次调用返回完整指令；
  - 同一 `loadedSkills` 内第二次调用同名技能不返回全文，返回"本轮已加载过"提示；
  - 不同 `loadedSkills`（新一轮）重新返回全文；
  - 技能名不存在时正常报错，不受去重状态影响；
  - 未传 `loadedSkills` 时仍能正常首次加载（防御性默认）。
- `npm test`：47/47 通过。
