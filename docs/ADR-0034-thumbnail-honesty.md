# ADR-0034: 缩略图诚实提示——`thumb` 字段透传到取回/渲染层，不喂给视觉模型装懂

- 状态：Accepted
- 类型：Bugfix / Honesty boundary
- 日期：2026-09-17
- 关联：ADR-0029（历史聊天附件安全取回，本记录复用其 `parseAttachment` 白名单与
  `wechat_fetch_chat_file` 取回链路）、ADR-0030（看图理解 `image_describe`，本记录要
  防止的错误场景正是发生在它身上）

## 问题（与方案无关）

同步端把群图片写进 `messages.attachment` 时，原图不一定已经到位——很多情况下只有一张
210×118、几 KB 的微信缩略图先同步过来。

机理（2026-09-17 实测确认，不要写成"等对方设备联网"——那是错的）：采集机
`PC-20211210FYMV` 上以助手账号（`wxid_6y9h8ldxbe2p22_5711`）登录着一个微信客户端，
采集脚本读的是**这个客户端的本地磁盘**。微信只有在**这个客户端自己显示过该图**时才把
原图落盘；群聊图片默认只落缩略图。所以原图到不到位，取决于采集机上那个客户端有没有
打开过对应会话，**与发图人的设备、与终端用户的手机都无关**。实测佐证：用户常打开的群
原图补齐率 74%–100%，从不打开的群 0%。

这不是本仓库能修的（见下方边界）。

真正的问题是：**agent 完全不知道自己手上拿到的是不是缩略图**。`wechat_fetch_chat_file`
把文件取回沙箱、`image_describe` 把它喂给视觉模型，模型看到一张 210×118 的糊图，不会说
"这图太小看不清"——它会**编出一段像样的描述**，语气笃定，用户根本分辨不出这段描述是真看到
了内容还是纯编的。

这比直接报错更有害：报错至少诚实地传达了"做不到"；而"编出一个描述"传达的是错误的自信，
用户会真的相信 agent 看到了图里的内容，据此做判断。这是一个**诚实性缺陷**，不是"某个功能
还没做"——功能（取图、看图）都是通的，缺的是"如实说明这次看到的是什么质量的数据"这一层。
即使把"透传 `thumb` 字段"这个具体方案整个拿掉，"模型不该在数据残缺时假装看清了"这个问题
依然成立，得靠别的方式解决（比如日后用图片尺寸做启发式判断）——只是同步端已经在消息里
明确写了 `thumb: true/false`，没有理由绕开这个现成的诚实信号去猜。

## 决策

### 1. `parseAttachment()` 补上 `thumb` 白名单透传

`src/services/wechat-log-store.mjs`：`a.thumb != null` 时 `out.thumb = Boolean(a.thumb)`，
与既有字段同一套白名单风格（未传时保持不存在，不凭空造出 `thumb: false`）。这是唯一的数据
入口改动——往下所有层都从这里拿到 `thumb`。

### 2. 提示打在"数据仍带着 `thumb` 标记"的那几层，不是 `image_describe`

选择在三个仍能看到 `attachment.thumb` 的地方给出提示，而不是在 `image_describe`：

- **`wechat_search_chat` / `formatResult`**（`wechat-tools.mjs` `renderBody`）：搜索结果里
  图片行追加"·目前只有缩略图，看不清内容"，agent 检索历史消息时就能看到。
- **`wechat_fetch_chat_file`**：取回成功后追加一行警告——"现在同步到的还只是缩略图……
  别拿它去 image_describe，模型看不清只会编；原图由采集端补齐，过一会儿再取一次可能就有了；
  如果一直没有就如实告诉用户没同步到原件，不要猜"——这是最关键的一层，
  因为**这正是 agent 决定要不要接着调 `image_describe` 之前看到的最后一条信息**。
- **`GroupCommandWatcher`**（群 @助手 入口的 `attachmentNote`）：图片附件提示里追加同样的
  警告，用户在群里发图 @ 助手时，agent 从一开始就知道这是张缩略图。

**为什么不选 `image_describe` 这一层**：`image_describe` 的入参只有沙箱内的文件路径
（`path`），从 ADR-0030 设计之初就是"不区分图片从哪来"的通用读图工具——它读到的是裸文件
字节，`thumb` 这个事实在文件落盘那一刻起就已经从"消息附件元数据"里脱钩了，除非额外发明一套
"文件路径 → 原始附件元数据"的旁路映射，纯属过度设计。真正掌握 `thumb` 事实的，是"文件还没
落盘、消息元数据还在手上"的那几层——把提示打在那里，成本最低，且天然覆盖了 agent 会看到
提示的所有入口（搜索、取回、群消息通知）。降级提示优于抛错：三处都是在原有成功输出后追加
一行文字，取回操作依然成功、消息依然能读，不会让整个工具调用失败。

## 本决策不解决什么（边界）

- **不修复原图缺失**：原图什么时候到位，取决于采集机上那个微信客户端有没有显示过该会话——
  这是采集端 `wechat-chatlog-dsh` 的"修复回扫"逻辑负责的，与本仓库无关。本仓库拿到的
  `thumb` 字段是只读的观察结果，不会、也不能主动催促同步。
- **不会在"用户从不打开的群"里让原图凭空出现**：这类群的图会一直停在缩略图状态——本决策
  的目标只是让 agent/用户对此保持知情，不是让原图消失的问题消失。
- **不基于图片实际尺寸/字节数做启发式判断**：完全依赖同步端写入的 `thumb` 字段；如果同步端
  某个消息漏写了这个字段（老数据、或某种消息类型未来才补齐这段逻辑），本决策不会追加兜底
  检测——那是另一个问题，出现了再单独处理。

## 备选（不选的理由）

- **在 `image_describe` 里按文件尺寸/字节数猜是不是缩略图**：210×118、7986 字节只是"典型"
  样本，不是协议保证的固定值——写一个尺寸阈值等于自己发明一套不可靠的启发式，而同步端已经
  明确给了 `thumb` 这个字段，没理由舍近求远。
- **`thumb: true` 时让 `wechat_fetch_chat_file` 直接拒绝取回**：用户可能仍想先看一眼糊图/
  凑合用，拒绝取回是过度保护；提示 + 仍然给文件，把判断权交还给 agent/用户，更符合本仓库
  一贯的"降级提示优于硬拦截"风格（同 ADR-0029 对 `available:false` 的处理方式一致）。

## 验收标准（可观察）

- `parseAttachment()` 对 `thumb: true`/`thumb: false`/字段缺失分别返回 `thumb === true`/
  `thumb === false`/键不存在——不会凭空发明这个字段。
- 搜索结果（`wechat_search_chat`）里 `thumb: true` 的图片行包含"只有缩略图"文案；
  `thumb` 为 `false`/缺失的图片行与改动前完全一致（无新增文案）。
- `wechat_fetch_chat_file` 取回 `thumb: true` 的图片时，成功文案里追加"只是缩略图"+
  建议稍后重试的提示；`thumb` 为 `false`/缺失时，输出与改动前逐字节一致（回归测试锁定）。
- 群 `@助手` 消息带 `thumb: true` 图片附件时，投给 agent 的 prompt 里出现"只同步到缩略图"
  提示；`thumb` 为 `false`/缺失时 prompt 不受影响。
- 以上四条均不会导致工具调用失败或抛异常——缩略图场景下取回/搜索仍然成功，只是多了一句
  如实的提示。

## 遗留风险

- **`image_describe` 本身仍会无条件把任何路径的图片送进视觉模型**：提示打在"取回"这一步
  是"劝阻"而不是"拦截"——如果 agent 无视提示、仍然对着已知的缩略图调用 `image_describe`，
  视觉模型依然会编。这是接受的风险：ADR-0030 的既有设计就是把"要不要看图"的判断权交给
  agent，本决策延续这个风格，只是把判断所需的事实摆到了它面前。
- **`thumb` 字段的真实性完全依赖采集端**：如果 `wechat-chatlog-dsh` 那边把 `thumb` 写反、
  或者原图已经补齐但字段没更新，本仓库会照单全收地转达一个过时/错误的提示——这是"如实
  透传上游数据"天然带的风险，不在本仓库能控制的范围内。
- **没有覆盖 `video`/`sticker` 等其它可能带缩略图概念的附件类型**：目前观察到的 `thumb`
  字段只在 `image` 类型上出现过，`parseAttachment` 的透传是 kind-agnostic 的（任何 kind
  只要带了 `thumb` 字段都会透传），但下游三处提示文案目前只针对 `image` 分支触发；如果
  未来 `video` 等类型也开始携带 `thumb`，需要另外确认是否要加对应提示。
