# ADR-0037: 1:1/网页对话默认不发 ack 与心跳

- 状态：Accepted（**代价条款被 ADR-0038 收窄**：同日晚些时候上线的固定反馈管道
  给 task 类消息加了 ~3s 受理回执——那不是本记录砍掉的通用 ack（无信息量、
  慢于阈值），而是有内容的理解确认。本记录的核心结论——chat 类消息一条直答、
  无 ack 无心跳——原样有效，"慢轮次零反馈"的承担范围缩小到分诊误判场景）
- 类型：Product / UX（**部分取代 ADR-0023** 的"8 秒延迟 ack + 40 秒心跳"条款）
- 日期：2026-09-18
- 关联：**ADR-0023**（长任务进度反馈——其 `createProgressNotifier` 组件、"失败必告知"
  条款、群命令入口的 ack 全部保留；本记录只改 1:1/网页路径的默认值）、
  ADR-0024（其"删除定期播报"的表述与代码长期不一致，本记录一并了结，见下）、
  ADR-0036（任务板：长活反馈的新 owner）

## 问题

ADR-0023 的 8 秒 ack 假设"8 秒还没答完 = 这是个长活"。该假设在当前生产已不成立：

实测（2026-09-18 14:54，生产 `/api/chat`，真实模型 `deepseek-v4-flash`）：

| 问题 | 端到端耗时 |
|---|---|
| 「现在几点」 | 7.6 s |
| 「你好」 | 8.8 s |

**基线延迟已经压在阈值上**，于是连打招呼都会先收到一条「✅ 收到，正在处理，请稍候…」
再收到答案——一问两条消息。用户反馈："我问一个简单的问题，他也会显示收到正在处理"。

把方案拿掉后依然成立的问题：**"这轮要多久"无法用固定毫秒阈值判定**——它随模型、
prompt 体积（本轮刚加了 5 个任务板工具描述）、串行队列排队情况漂移，任何写死的阈值
都会在某次变更后失效，而失效方向是"对所有人多发一条废话"。

## 决策

`createProgressNotifier` 的 `ackDelayMs <= 0` 语义化为**整体关闭**（`start()` 变 no-op，
既不 ack 也不心跳）；`MessageRouter` 的 `progress` 默认值改为 `ackDelayMs: 0`，
即 **1:1 微信对话与网页对话默认完全静默**，用户只收到答案一条。

理由不是"用户嫌吵"这一条，而是**职责已经转移**：长活的反馈通道现在是任务板
（ADR-0036）——建单即人话确认、`activeForm` 心跳、完成即推送。主 agent 轮次里
残留的长活是**判据失灵的症状**（该落板没落板），这时 ack 的作用是把症状包装得
舒适，反而让问题不可见。

**保留不动**：
- 组件本身与群命令入口的 ack（`GroupCommandWatcher` 显式传 `ackDelayMs: 5` 起的
  配置，生产走 ADR-0023 默认 8 s）——群里 @助手、结果走私聊 DM 是**跨渠道**，
  "助手收到了没"这件事没有别的表面能回答，与 1:1 同线程的延迟感知不是同一个问题；
- ADR-0023 的"失败必告知"条款（在 `message-router.mjs` 的 catch 里，与 notifier 无关）。

**可逆**：`CHAT_PROGRESS_ACK_MS` 可重新开启。若将来确实需要，应设**远高于基线**的值
（如 45000），而不是恢复 8000——恢复 8000 等于把本 ADR 的问题原样请回来。

**顺带了结一处长期漂移**：ADR-0024 §7 声称"删除 40 秒定期播报"，但
`progress-notifier.mjs` 的 `intervalMs=40_000, maxHeartbeats=5` 一直在代码里且
生产未覆盖参数（DESIGN-agent-task-board §3.6 已记录此不一致）。现在 1:1 路径
整体关闭，该表述在主路径上**终于与代码一致**；群路径仍有心跳，且已在此处写明。

## 备选

- **只把阈值从 8 s 提到 45 s**：能消掉噪音，但把同一个"写死阈值会再次失效"的问题
  留到下一次模型/prompt 变更。落选——不过该值作为可逆开关的推荐值保留在上文。
- **按问题类型预判要不要 ack**：需要在 LLM 回答之前判断复杂度，而"判据不能靠估
  耗时"是 ADR-0025 已经付过学费的结论。落选。
- **保留 ack 但改成流式输出**：iLink 消息通道无流式语义，超出本次范围。

## 后果

- 正面：简单问答从两条消息回到一条；长活反馈集中在任务板一处，语义唯一。
- 代价（明确承担）：若 agent 误判、在主轮次里闷头跑了一个长活，用户在结果到达前
  **零反馈**。这是有意选择——让判据失灵可见，而不是用 ack 掩盖。观测手段是
  `AgentTaskStore.stats()` 与用户"你还在吗"这类追问。
- 放弃：1:1 路径"任何慢轮次都有兜底反馈"这个保证。

## 验证（2026-09-18 实际执行）

- Passed: `node --test tests/progress-notifier.test.mjs tests/message-router.test.mjs
  tests/group-command-watcher.test.mjs` → 22/22。新增三条：
  - `ackDelayMs <= 0` 彻底静默（0 与 -1 两种输入）；
  - **负向保证**：不传 `progress`（= 生产装配路径）时慢轮次只发结果一条；
  - `CHAT_PROGRESS_ACK_MS` 显式开启后机制仍在（能力没被删掉，只是默认关）。
  既有"慢轮次有 ack""快轮次无 ack""群命令 ack"三条测试均显式传参，原样通过
  ——证明改的是默认值而非能力。
- Passed: `node --test --test-concurrency=1 "tests/*.test.mjs"` → 512/512（全量回归）。
- Inspected: 生产实测延迟数据（上文表格）即本决策的事实依据。

## 遗留

- 基线 8-9 秒本身偏慢（简单问答也要走完整 agent loop + 记忆召回 + 现已增至
  五个任务板工具的描述）。**本记录不处理**，只如实记下：它是本决策的成因，
  也是独立于本决策的优化空间。
- 群命令路径的 ack 未按同样方式复核（其基线耗时未实测）。
