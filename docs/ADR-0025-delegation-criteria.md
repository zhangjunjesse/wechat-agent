# ADR-0025: 委派判据重构——按操作类型判定，判据放进"必然可见"的表面

- 状态：Accepted
- 类型：Architecture / Prompt（判断力）
- 日期：2026-09-16
- 前身：`docs/DESIGN-task-delegation.md`（working proposal，已同步更新第 3/4/5/6 节）
- 关联：**ADR-0024（部分取代：其"决策 3 关键技术点·判断力三层"的 ① 四条硬判据与 ② 技能装判据）**、
  ADR-0023（长任务进度反馈）、ADR-0013（技能动态加载）、ADR-0022（群命令入口）
- 触发：生产事故（真实会话）

## 问题（真实事故）

用户：「把这个飞书文档下载给我」。主 agent **没有派发**，直接在主对话里调用 `lark_export_doc`
等待（异步导出 + 轮询，10–60 秒），期间用户连问「在吗」「好了吗」，主 agent 被这一轮 run 占住，
体验比"派出去"更差。agent 事后自述的理由是：

> 我认为只有一次工具调用，不算"多步任务"，所以没派。

这不是"模型不听话"，而是**判据本身是错的**。

## 根因分析

| # | 根因 | 说明 |
|---|---|---|
| A | **判据用错代理指标** | ADR-0024 的"多步 = ≥3 次工具调用 / 预计 ≥30 秒"是**对耗时的代理**。`lark_export_doc` 是一次调用却跑 10–60 秒 → "数调用次数"与"估时间"都会**系统性漏判单步但慢**的操作。 |
| B | **规则放在不可靠可见的表面** | 判据写在 ① 长静态 prompt 的一段里 ② `skills/task-delegation`（ADR-0013 **按需加载**）里。skill 不 `use_skill` 就不在上下文——判据等于默认缺席；而**每轮必然在场**的 `delegate_task` 工具描述当时完全没写判据。 |
| C | **没有"进行中任务"的意识** | 任务会在多轮里长大（先 PDF → 再要 Word → 再要 HTML），但没有规则要求**动手前先 `list_tasks`**，于是每轮都当新活自己干，既重复又占用主对话。 |
| D | **派发路径的可见性低于自己动手** | 自己做：用户看到"正在输入"、能追问；派发后：只有一句"已派发"，`task_status` 当时也不给已用时长 → 用户压力（"在吗/好了吗"）反而把 agent 逼回自己动手。**可见性是判据能否被遵守的一部分**，不是附加项。 |

## 决策

### 1. 判据从"耗时估计"改为**操作类型清单**（根治 A）

命中任一类型且任务自包含 → **默认派发**：

1. 导出/下载文件（飞书文档导出、附件下载、大文件转换）；
2. 批量处理（多文件、多数据、多群/多次发送）；
3. 生成文档/图片/海报/报告；
4. 抓取多篇内容再汇总；
5. 要等外部异步接口（导出任务、长轮询、第三方处理）。

并**显式禁止错误代理**：「判据看操作类型，不要靠估时间、也不要看自己调了几次工具」。
`DELEGATE_MIN_SECONDS` 随之删除（判据换成类型后它没有语义，留着就是漂移）。

### 2. 判据搬家到"每轮必然可见"的表面（根治 B）

| 表面 | 可见性 | 承载什么 |
|---|---|---|
| `delegate_task` **工具描述** | 每轮都在上下文，模型选工具时必然读到 | **完整判据**（操作类型清单 + 不适用清单 + 派发前查重 + 派发后纪律） |
| `PACE_RULES` 静态规则（第 4/5/6 条） | 每轮（静态 instructions） | 判据摘要 + 派发前查重 + 派发后纪律 |
| `skills/task-delegation` | **仅按需** | **降级为细节手册**：goal 模板、汇报话术、反例表（不含判据） |

原则：**判据属于"必然可见"的表面，细节属于"按需加载"的表面**。skill 的 description 明确
写"判据不在这里"，防止模型指望 skill 来决策。

### 3. 慢工具自我声明（根治 A 的另一半）

光有清单不够——模型还得知道"这个工具本身很慢"。`lark_export_doc` 与 `image_generate`
的描述里加：**慢工具 + 单次调用就会卡住当前对话 + 主对话先派发 / 子任务直接执行**。
`notify_user` 的描述同步去掉"预计超过 30 秒"的秒数口径，改为长任务场景口径。

### 4. 派发前查重（根治 C）

`list_tasks` 的描述改为双用途（派发前查重 + 回答"我派的任务"），并在 `delegate_task`
描述与 PACE 第 5 条里都要求：**动手或派发前先 `list_tasks`**，已有同类进行中任务就报进度、不重复派。

### 5. 派发路径可见性 ≥ 自己动手（根治 D）

`list_tasks` / `task_status` 输出**已用秒数**（`执行中 · 已用 42 秒`）：用户催问时 agent 能
如实回答"还在处理中，已用 42 秒"，而不是含糊其辞或干脆自己重做一遍。

## 备选（不选的理由）

- **只加强 prompt（"要记得派发！"）**：根因 B 说明判据当时就不在可靠表面，加强措辞不解决可见性。
- **把秒数阈值调低（如 ≥10 秒）**：仍是时间估计，模型估不准；且会把大量秒级操作误判为长任务。
- **让工具自己决定是否委派（工具内自动派生后台任务）**：主 agent 失去"要不要派"的表达，
  且用户看不到"已派发"的确认；判据不透明，出问题无法归因。
- **把判据留在 skill、每轮强制加载 skill**：等价于把细节手册当常驻 prompt，token 成本高于写进工具描述。

## 验收证据

- 单测：`node --test tests/delegate-tools.test.mjs` **7/7 通过**（新增 2 条）：
  - `delegate_task` 描述含操作类型清单、`判据看操作类型`、`list_tasks`、`不要承诺具体结果`，
    且**不再含秒数阈值**（`/\d+\s*秒/`、`minSeconds` 断言取反）——防止错代理指标回归；
  - `task_status` / `list_tasks` 对进行中任务输出 `已用 N 秒`。
- 全量：`node --test tests/*.test.mjs` → **329/329 全绿**（ADR-0024 基线 324 + 新增 5：
  delegate-tools 2——描述承载操作类型判据且**不含秒数阈值**、进行中任务输出已用秒数；
  其余 3 为 ADR-0024 之后的小幅用例增长）。
- 端到端：生产部署后由真实会话验证（见"遗留"的 H1/H2/H3）。

## 遗留（诚实边界）

- **效果未实测**：本记录只完成"判据与可见性重构 + 单测"，真实委派率需要生产会话验证。可证伪假设：
  - **H1** 只加强 prompt（不动工具描述）→ 单步慢任务的委派率仍≈0；
  - **H2** 把"慢工具+操作类型"写进工具描述后 → 该类任务委派率上升（本 ADR 预测成立）；
  - **H3** 不做派发前 `list_tasks` → "任务在多轮里长大"的场景仍会漏判。
- **校准指标仍在**：`TaskRunStore.stats()` 的短任务派发率（判据过松）与失败率（goal 写法）。
  "该派没派"目前只能靠会话观察，尚无自动指标（主 agent run 时长未落库）。
- **ADR-0024 的架构不动**：独立 agent 实例、`ephemeral`、受限工具集、队列、超时、落库、通知纪律全部保留。
